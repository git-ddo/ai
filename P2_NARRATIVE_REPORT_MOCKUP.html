Gitddo 백엔드는 무엇을 보여주는가

git-ddo/backend
사용된 분석 깊이 P0 · 구조 P1 · 활동 P2 · 코드 구간 Narrative AI 가정

프로젝트 개요와 공개적으로 확인되는 구성

Gitddo 백엔드는 Java 21과 Spring Boot를 중심으로 GitHub 포트폴리오 분석 요청을 처리하는 서버 프로젝트입니다. 의존성 파일에서는 Spring Data JPA, Spring Security OAuth2 Client, PostgreSQL, Flyway와 Testcontainers가 함께 확인되며, 이는 인증과 영속성, 데이터베이스 마이그레이션, 격리된 테스트 환경을 포트폴리오에서 설명할 수 있는 구체적인 출발점이 됩니다. ev_001

README에는 단순한 프로젝트 소개만이 아니라 기술 구성, GitHub OAuth 설정, 로컬 실행 방법, 환경 변수, Swagger, Repository 조회 API와 포트폴리오 평가 흐름이 정리되어 있습니다. 따라서 처음 저장소를 접하는 사람이 서비스의 목적과 실행 절차를 따라갈 수 있는 문서 근거가 확보되어 있습니다. 테스트 디렉터리에서는 분석 수집기, 요청 조립기, 응답 Validator와 HTTP Client 등을 대상으로 한 테스트 파일 15개가 관찰되며, compose.yml에는 PostgreSQL 17 컨테이너의 healthcheck와 영속 볼륨 설정이 존재합니다. ev_002 ev_003 ev_004

P1 활동과 P2 코드 구간이 보여주는 구현 범위

P1 활동 근거에서는 커밋 0f33058을 통해 P1 Evidence 수집기, 활동 영향도 정책, AI 요청 조립기와 AI 응답 Validator가 함께 변경된 사실이 확인됩니다. 이 기록은 해당 영역에서 변경 활동이 있었다는 점만 보여주며 개인 기여율이나 숙련도를 증명하지는 않습니다. ev_006

P2에서 제공된 P1EvidenceCollector.java 113~153행은 PR을 영향도 기준으로 제한하여 선택하고, 제한을 초과한 경우 Warning과 PR Evidence를 생성하는 흐름을 보여줍니다. 포트폴리오에서는 이를 “외부 API에서 가져온 모든 데이터를 무조건 사용하지 않고, 정해진 예산과 영향도 정책에 따라 분석 입력을 제한하는 수집 흐름”으로 설명할 수 있습니다. 다만 이 판단은 제공된 코드 구간에 한정되며 수집기 전체 구현의 품질을 평가한 것은 아닙니다. ev_007

이어서 AiAnalysisResponseValidator.java 47~60행에서는 요청에 포함된 Repository, Evidence와 UserClaim의 ID 집합을 구성한 뒤, 분석 깊이와 Repository 범위, 코칭 결과의 참조를 순차적으로 검증하는 흐름이 관찰됩니다. 이 구간은 AI가 생성한 문장을 그대로 저장하지 않고, 요청에 존재하는 근거만 참조하는지 확인하는 방어 계층을 설명할 때 활용할 수 있습니다. ev_008

PORTFOLIO APPEAL

이 Repository의 핵심 어필 포인트는 “GitHub 데이터를 수집하는 기능” 자체보다, 수집 범위를 제한하고 AI 결과가 허용된 Evidence를 참조하는지 검증하는 파이프라인을 설계했다는 설명에 있습니다.

보완하면 좋은 설명

현재 고정된 Snapshot의 수집 대상 파일 트리에서는 .github/workflows 아래의 Workflow가 관찰되지 않았습니다. 이는 실제로 CI/CD가 존재하지 않는다는 뜻이 아니라, 이번 수집 범위에서 확인하지 못했다는 의미입니다. ev_005

근거 기반 보완 제안

CHAPTER 02 · REPOSITORY ANALYSIS

졸업요건 도메인을 코드로 설명하는 프로젝트

congraduation-team/congraduation-backend
사용된 분석 깊이 P0 · 구조 P1 · 활동 P2 · 코드 구간 Narrative AI 가정

프로젝트 개요와 공개적으로 확인되는 구성

Congraduation 백엔드는 Java 21, Spring Boot 3.3, Spring Data JPA와 MySQL을 기반으로 졸업요건을 진단하는 서비스입니다. Apache POI와 Jsoup 의존성이 함께 관찰되므로 문서 또는 외부 데이터 처리와 연결되는 기술 구성을 확인할 수 있지만, 구체적인 사용 방식은 이번 P2 코드 구간에 포함되지 않았으므로 의존성 존재 이상으로 단정하지 않습니다. ev_009

README는 문제 정의와 핵심 기능, 기술 스택, 아키텍처, 실행 방법, 테스트 명령, 주요 API와 프로젝트 구조를 포함합니다. 테스트 디렉터리에는 졸업요건 정책, 로드맵, 인증, ABEEK, 파서와 서비스에 관한 테스트 파일이 관찰되고, Docker Compose에는 로컬 MySQL 실행 구성이 있습니다. 이 조합은 도메인 규칙을 다루는 프로젝트를 다른 사람이 실행하고 검증하기 위한 문서와 테스트의 외형적 근거를 제공합니다. ev_010 ev_011 ev_012

P1 활동과 P2 코드 구간이 보여주는 도메인 구현

커밋 8c8f619에서는 2021학번 공통교양 필수 정책 코드와 그에 대응하는 테스트가 함께 변경된 사실이 관찰됩니다. 변경 경로는 정책 로직과 검증 코드가 같은 활동 범위 안에서 다뤄졌음을 보여주지만, 해당 변경의 개인 기여율이나 전체 설계 품질을 의미하지는 않습니다. ev_014

BalancedLiberalCoursePolicyService.java 34~43행에서는 2021학번에 적용되는 공통교양 필수 과목 목록이 상수로 분리되어 있습니다. 이 코드 구간을 면접에서 설명할 때는 학번에 따라 달라지는 졸업 정책을 어떻게 표현하고, 새로운 학번 정책이 추가될 때 무엇을 변경해야 하는지를 중심으로 이야기할 수 있습니다. 다만 상수 분리 자체가 확장성을 보장한다고 단정할 수는 없으며, 실제 정책 선택 구조는 추가 코드 확인이 필요합니다. ev_015

GraduationProgressServiceTest.java 891~936행에서는 2021학번 학생과 여덟 개의 공통교양 이수 데이터를 구성하고 추출 결과를 검증하는 사례가 직접 확인됩니다. 따라서 포트폴리오에서는 “정책 목록을 선언했다”에서 멈추지 않고, 해당 정책이 실제 학생 데이터에 적용되는 시나리오를 테스트로 남겼다는 점까지 연결해서 설명할 수 있습니다. ev_016

PORTFOLIO APPEAL

이 Repository는 복잡한 졸업요건을 단순 CRUD가 아닌 학번별 정책과 검증 시나리오로 표현한 경험을 보여주는 보조 프로젝트로 활용할 수 있습니다.

배포 과정에서 보완할 수 있는 지점

.github/workflows/deploy.yml에는 main 브랜치 push 시 Java 21 환경에서 bootJar를 빌드하고 EC2로 전송한 뒤 서비스를 재시작하는 흐름이 있습니다. 배포 자동화 자체는 공개 근거로 확인되지만, 현재 Workflow는 테스트를 제외하고 빌드합니다. ev_013

근거 기반 보완 제안

배포 단계 앞에 테스트 실행을 독립 Job 또는 Step으로 추가하고, 테스트 통과 이후에만 배포가 진행되도록 구성하면 현재 존재하는 테스트 코드와 배포 자동화를 하나의 품질 확인 흐름으로 연결해 설명할 수 있습니다.

전체 포트폴리오에서 드러나는 공통 축

두 Repository는 모두 Java와 Spring Boot를 사용하지만, 포트폴리오에서 보여주는 역할은 서로 다릅니다. Gitddo는 외부 GitHub 정보와 AI 결과 사이의 근거 경계, 수집 예산과 응답 검증을 설명하는 데 적합하고, Congraduation은 학번별 졸업 정책을 코드와 테스트 시나리오로 연결하는 도메인 구현 사례로 활용할 수 있습니다.

이 차이를 유지하면 포트폴리오가 동일한 기술 스택을 반복해서 나열하는 대신, 첫 번째 프로젝트에서는 “신뢰할 수 없는 외부 데이터와 AI 응답을 어떻게 제한하고 검증했는가”를, 두 번째 프로젝트에서는 “복잡한 정책 규칙을 어떻게 코드와 테스트 데이터로 표현했는가”를 각각 설명할 수 있습니다. 이는 실제 P2 코드 구간에서 확인된 책임을 바탕으로 한 구성 제안이며, 두 저장소 전체의 아키텍처 품질을 비교하거나 사용자의 숙련도를 평가한 결과는 아닙니다.
